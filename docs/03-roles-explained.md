# 03. 各役割の解説

対応表に出てくる「役割」を、何をするものか・いつ必要になるかの観点で説明する。
似た役割をまとめて5系統に分類。

## アプリを動かす系

「書いたコードをどこで走らせるか」。小さい順に 関数 → コンテナ → 仮想マシン と、自由度が上がるぶん手間も増える。

| 役割 | 何をするもの | いつ必要になるか | 例え |
| --- | --- | --- | --- |
| ホスティング | Web アプリを公開し続ける | サイトやアプリを人に使ってもらうとき | 店舗を借りて営業 |
| コンテナ（サーバーレス） | Docker イメージをリクエスト時だけ動かす | Next.js や API サーバー、特殊ライブラリ | 必要なときだけ開く移動販売車 |
| コンテナ（Kubernetes） | 多数のコンテナを自動で並べ、落ちたら立て直す | 常時大量アクセス、マイクロサービス10個以上 | 店舗網を本部が一括管理 |
| 仮想マシン | OS ごと1台借りて自由に使う | 常駐プロセス、GPU、特殊ソフト | 一軒家を借りる |
| 関数 | 1つの処理だけ書いてイベントで起動 | Webhook 受け口、画像変換など | 呼び鈴が鳴ったら出る |
| エッジ実行 | 利用者に近い拠点で軽い処理 | リダイレクト、A/B テスト、認証チェック | 各地の営業所で済ませる手続き |
| 定期実行 | 決まった時刻にジョブを起動 | 毎朝の集計、1時間ごとの API 取得 | 目覚まし時計 |
| 静的サイト | HTML/CSS/JS をそのまま配る | LP や会社サイト | チラシを置くだけ |

**選び方**
- まず「関数で済むか」を考える。済めば一番安くて楽
- Web アプリ本体や依存が多い処理はコンテナ（Cloud Run）
- Kubernetes と仮想マシンは必要になるまで触らない
- 定期実行は「時計」なので、動かす本体と必ずセット

## データを置く系

| 役割 | 何をするもの | 向いているデータ | 例え |
| --- | --- | --- | --- |
| リレーショナル DB | 表形式で保存、SQL で結合・検索。整合性が強い | 顧客・注文・商品など行と列で表せるもの | Excel の表を厳密にしたもの |
| NoSQL | JSON のような柔軟な形で保存 | ユーザー設定、チャット、ログ | 付箋を箱に入れる |
| オブジェクトストレージ | 画像・PDF・動画などファイルをそのまま置く | 商品画像、帳票、バックアップ | 倉庫の棚 |
| キャッシュ | メモリに一時保存して高速に返す | セッション、ランキング | レジ横の売れ筋棚 |
| データウェアハウス | 大量データを列単位で保存し集計に特化 | 広告データ、アクセスログ、売上の数年分 | 全店舗の売上を集めた分析室 |
| KV ストア | キーと値の組だけを超高速に読む | 設定値、フラグ | 鍵付きロッカー |
| ベクトル検索 | 文章や画像を数値化して「意味が近いもの」を探す | RAG、類似商品検索 | 似た雰囲気の服を探す店員 |

**RDB と DWH の違い**
- RDB は「1件ずつ読み書き」が得意。アプリの裏側に置く
- DWH は「数億行をまとめて集計」が得意。レポートや分析に置く
- アプリのデータは RDB（Supabase）、分析したい分だけ DWH（BigQuery）に流すのが定石

**ストレージと DB の違い**
- ファイルそのものはストレージへ
- 「そのファイルがどの商品のものか」は DB へ。DB には URL だけ保存

## つなぐ・流す系

| 役割 | 何をするもの | いつ必要になるか | 例え |
| --- | --- | --- | --- |
| メッセージング（Pub/Sub） | 「〇〇が起きた」を投げておき、受け手が好きなタイミングで処理 | Webhook を受けてすぐ返事し、重い処理は後回し | 回覧板・郵便ポスト |
| ワークフロー | 複数の API 呼び出しを順番・条件分岐付きで実行 | 「取得→変換→保存→通知」のように段階が多い | 業務フロー図を自動で回す |
| ETL | 取り出し・整え・入れる | 外部 API や CSV を DWH に定期取り込み | 原材料を加工して倉庫へ |
| Webhook 受け口 | 外部サービスからの通知を HTTP で受ける | Shopify の注文、Meta の投稿更新 | 会社の代表電話 |
| Data Transfer Service | Google Ads・GA4 などを BigQuery に自動取り込み | Google 系データを分析したいとき。コード不要 | 自動で届く定期便 |
| スケジュールドクエリ | BigQuery の SQL を定期実行して集計表を更新 | 毎朝のレポート用テーブル | 毎朝の自動集計 |

**典型的な流れ（Paletto の例）**
1. Instagram の投稿更新 → Webhook 受け口（Cloud Run functions）
2. 受け口はすぐ「受け取った」と返し、内容を Pub/Sub に投げる
3. Pub/Sub を購読する Cloud Run jobs が Meta API に問い合わせて BigQuery に書く
4. スケジュールドクエリが毎朝テナント別に集計

**Pub/Sub が要らないケース**
- 処理が数秒で終わり、失敗しても再実行で済む → 関数の中で直接
- テナントが数社で1日数回 → Scheduler + Cloud Run jobs で十分

## 守る・届ける系

### 中の人を守る

| 役割 | 何をするもの | いつ必要になるか | 例え |
| --- | --- | --- | --- |
| 認証（利用者） | ログイン・パスワードリセット・SNS ログイン | アプリに利用者アカウントがあるとき | 会員証の発行 |
| 権限管理（IAM） | 開発者やサービスが「どの機能を使えるか」 | 複数人で開発、本番と検証を分ける | 社員証で入れる部屋を決める |
| サービスアカウント | プログラムに渡す身分証 | Cloud Run から BigQuery を読むとき | 配達員の社員証 |
| シークレット | API キー・DB パスワードを暗号化保管 | 常に | 金庫 |
| 行レベルセキュリティ | DB の行ごとに「誰が見られるか」 | マルチテナント | 社員ごとに見える棚を分ける |

### 外から来る通信をさばく

| 役割 | 何をするもの | いつ必要になるか | 例え |
| --- | --- | --- | --- |
| DNS | ドメイン名を IP に変換 | 独自ドメイン（常に） | 電話帳 |
| CDN | 静的ファイルを世界中の拠点から返す | 画像が多い、海外アクセス | 各地の配送センター |
| ロードバランサー | 1つの入口から複数サーバーに振り分け。HTTPS 終端 | サーバー2台以上、独自ドメイン + HTTPS | 受付で窓口に振り分ける人 |
| WAF / DDoS 対策 | 攻撃パターンを入口で止める | 公開 API がある | 警備員 |
| 証明書管理 | HTTPS 証明書の発行・更新 | 独自ドメインで HTTPS | 営業許可証の更新 |

**GC での注意点**
- GC では CDN・WAF・証明書がすべてロードバランサーにぶら下がる。Cloud Run 単体でも動くが、独自ドメイン + CDN なら LB が必要
- Cloudflare を前に置けば DNS・CDN・WAF・証明書を全部 Cloudflare で済ませられる。小規模はこの構成が多い
- 認証は Supabase Auth を残してよい

## 作る・運用する系

| 役割 | 何をするもの | いつ必要になるか | 例え |
| --- | --- | --- | --- |
| CI | push のたびにテスト・ビルドを自動実行 | 壊れたコードを本番に出したくない | 出荷前の検品 |
| CD | テストが通ったら自動デプロイ | 手作業のデプロイをなくしたい | 検品が通ったら自動出荷 |
| コンテナレジストリ | Docker イメージの倉庫 | Cloud Run を使うなら必須（自動） | 完成品の倉庫 |
| パッケージ配布 | 自作 npm / pip ライブラリを社内配布 | 共通コードを使い回す | 社内部品カタログ |
| ログ | 出力を集めて検索可能に | エラー調査（常に） | 業務日誌 |
| 監視・アラート | CPU・エラー率を見て閾値超えで通知 | 本番で落ちたことに気づきたい | 警報装置 |
| トレース | 1リクエストがどこを何ミリ秒通ったか | 遅い原因が分からないとき | 配送の追跡番号 |
| 生成AI（Vertex AI） | Gemini / Claude を API で呼ぶ | LLM を本番で使う、請求を GC にまとめたい | 外部の専門家窓口 |
| 機械学習基盤 | 自前モデルの学習・デプロイ | 独自の予測モデル | 自社研究所 |

**GC での注意点**
- CI/CD は Cloud Build を使わず GitHub Actions から `gcloud run deploy` が一番楽
- ログは Cloud Run で標準出力に書けば勝手に集まる
- 監視は「エラー率が上がったらメール」1本で十分
- Vertex AI 経由で Claude を呼ぶと請求が GC にまとまる。新モデルの提供は Anthropic 直接契約の方が早い
